A request, a measurement, an evidence trail

Illustration · no live systems

This walk-through follows one file request into PowerScale, then shows how its storage statistics are collected beside that path, and what evidence we keep. Every example is illustrative: no live system was queried, and nothing here changes a collection setting.

A scan application needs file data

A user opens a scan. The application runs on a server or a VM and needs file data that is stored on PowerScale. This starts the example; no collector is involved yet.

The request travels to PowerScale

The application asks its operating system for the bytes. The VM's file client sends an SMB or NFS request. The network carries requests and file bytes between systems. PowerScale's operating system, OneFS, serves the shared file using its storage nodes.
A write follows the same route: "store these bytes at this position". One user click can cause many file operations.

The reply travels back

The file data comes back the same way: PowerScale, the network, the VM, the application. Everything the user waits for is on this route, and only part of it is inside the storage system.

Receive, process, serve, respond

PowerScale is the shared storage product; OneFS is its operating system, and several storage nodes work together. A node receives a file operation through SMB or NFS. It checks access and locates the file data or metadata. It serves the read from cache or storage, or processes the write. Then it sends data, an acknowledgement or an error back to the client.
This is a simplified flow, not an exact execution trace for every operation. Reference: Dell OneFS technical overview (see the Read lens).

Where storage latency is measured

Storage latency has a measurement boundary: it describes the work covered by that storage metric. The user also waits for the application and the rest of the path, so a delay inside this box is only one part of the user's wait.

PowerScale already keeps statistics

While serving file operations, the system maintains counters and performance measurements, and an API exposes them grouped. Activity: operation counts, rates and bytes transferred, where the endpoint supplies them. Latency: time spent processing the operations the metric covers. Who and where: client address, protocol, operation class and storage node, where reported.

A small example

Illustration only. Imagine ten measured reads whose durations add up to 120 milliseconds. Their average is 12 milliseconds per operation.

Read an average with care

That does not mean every read took 12 milliseconds, or that the user saw the scan in 12 milliseconds. A returned average alone cannot recover each request, its maximum or its percentiles. Keep the units, the operation group and the measurement interval with the number.

A separate request asks for statistics

Our collector makes a management API request on its own schedule. It is a second, separate request, outside the application's file-data path.
Two meanings of "request": the application's file request opens or changes a file; the collector's API request reads management information about activity.

Two requests, two paths

The user's file request goes to PowerScale. Separately, the collector asks the management API for statistics. The file bytes never pass through the collector, and real reads and writes carry on between collection runs.

Each poll's rows land in InfluxDB

A timer starts a poll; it is not triggered by each application request. The collector asks PowerScale for selected statistics, receives rows and metadata, and records success, partial results, a timeout or an error. The existing Python collection writes the measurements to InfluxDB.

It polls on a schedule

Reported operator settings, still to be confirmed against the deployment; they are not PowerScale defaults. Client performance every 5 seconds, to notice short changes. A full performance pass every 5 minutes: system, drives, protocols, nodes, heat, network, jobs and sessions. Configuration every 6 hours at minute 05, protection every hour at minute 35, events every hour at minute 20.
Collection time is when we asked; an event's own timestamp is when it reportedly happened. An inventory snapshot shows what was seen then, not that it stayed true for six hours.

What one row means

A row usually describes a population of operations, not one named application request. Top-N selection keeps only the selected clients. A poll time alone does not establish the metric's time window.

One click, many operations

A poll is not a trace of this request. One click can cause many file operations; our rows describe groups of operations and keep only selected clients, so we cannot assign the user's total wait to one read from those averages.

Units travel with the number

The Python collection stores these latency fields in microseconds: 1,000 microseconds is one millisecond. Every number keeps its unit, its operation group and its interval.

Zoom into the data

Now we close in on the collector and follow one poll's data from the device's response to a finding. One small synthetic example, an illustration: the addresses come from the documentation range, and the fingerprint is made up.

The raw API response

The management API answers a poll with rows of client statistics. Each row has an address, a protocol, an operation class, a storage node, an operation count and an average time in microseconds. Three rows here, illustration only.

Top-N keeps rows, each with a reason

Top-N selection keeps a few clients per poll and records why each was kept: a high rate, many bytes, a peak, or a typical row kept for comparison. The busy first row is kept for its rate, the slow third row for its peak. The second row is not selected: it stays in the response, but no saved row will carry it.

Each kept row gets an address

A kept row is addressed by a pointer into the response it came from, /client/2 (the third element, counting from zero), together with the SHA-256 fingerprint of that exact response. Pointer plus fingerprint name one row of one response, so it can be found again.

The row lifts out…

The selected row leaves the response...

…and becomes a typed point

...and is written as one InfluxDB point in line protocol: a measurement name, tags that say who and where (address, protocol, operation, node), and fields that hold the values.

Every field keeps its type and unit

Field types are explicit: a float has a decimal point, an integer ends in i, a string is quoted, a boolean is true or false. A field written once as an integer and later as a float would be refused, so the writer fixes each type. Times stay in microseconds: 48,200 microseconds is 48.2 milliseconds.

One receipt per poll

Every poll gets a run receipt: when it started and ended, its status (ok, partial or timeout), how many rows it saw, kept and dropped, and the fingerprint of the response. The fingerprint is the same one the row's address carries, so the row and the receipt point at the same response.

Sixty polls, two gaps

At one poll every five seconds, a five-minute window holds sixty polls. Two came back without data here: one timed out, one is missing. Missing means unknown, not zero: the gaps stay gaps, and the window summary says so, mean and peak over 58 of 60 polls, never a zero folded into the mean. Illustration values.

A finding opens its trail backwards

A finding, "client latency high", opens its trail backwards, one step at a time: the statistic it was judged on, the window that statistic summarises, the receipt of the poll, the selected row with its reason, and the raw response it came from.

Python path: the trail starts at the database

Two evidence paths. The existing Python collection writes rows to InfluxDB and does not keep the device response, so a finding read from the database can be traced back only as far as the saved query result.

Native path: it starts at the device

The native Node collector keeps the captured response, its fingerprint and a receipt beside the rows it writes, so the trail runs all the way back to the device response. Those Node paths are built for clients, drives and system statistics, and are not yet switched on.

Every poll leaves a receipt

Back in the big picture: every poll leaves a receipt beside its rows. Python's additive evidence and raw-response archiving are separate options, off by default; nothing in this walk-through turns them on.

Footprint keeps the trail

Footprint records how a captured response is selected, converted and used for a finding, so a finding can be followed back to its statistic, its saved rows and the captured response. On the direct-capture path that reaches the saved device response; reading existing InfluxDB data, the trail stops at the saved query result unless the collection-run join and the archived response are available and verified.
What it does not prove: a trace of our processing is not a trace of the application's file request, and not proof of physical cause. Our evidence ID identifies the collected observation, not the application's request.

Ask a question

An illustrative investigation, not a measurement from a real system. A user says the scan is slow. What do we actually know?

What is known

Illustration: the saved PowerScale response reports this client's average read latency as 12 milliseconds. That fact stands on its own evidence. Whether it is abnormal needs a baseline or a configured rule.

What is not sure, and why

Which VM produced that traffic is unresolved, because the client-to-VM mapping for that time is missing. A timed-out poll is the same kind of gap: the answer names it instead of filling it in. Only the VM claim is blocked; the latency fact remains usable. Saying why it was slow would need more evidence again: a simultaneous job or warning is a clue, not proof of cause.

The trail opens on click

Clicking the known fact opens its trail: the finding, the statistic, the saved rows and the captured response it rests on, so anyone can check the answer instead of trusting it.

What is built

From the saved project checks of 20 October 2026, not a live deployment monitor. Three Node performance paths are implemented and tested: clients, drives and system statistics. They reuse the shared writer and produce traceable evidence. They are inactive: nothing starts them automatically, the existing Python collection continues, and VM mapping stays off. Compression is listed as built in the project checklist.

What is still pending

The operator's schedules still need confirming against the deployed settings. Retention and the throughput fix are open. Also still ahead: an approved storage policy, an independent service and a separate-bucket live comparison; Node writers for the remaining performance data; and the receipt and archive joins. The next gate is deciding evidence per run versus per window, then one small writer change at a time.

One picture, end to end

One request, one measurement, one evidence trail. The file path serves the user; PowerScale measures its own work; the collector reads those statistics beside the path; and every finding can be followed back to the response it came from.
