The request

One file request, a measurement, an evidence trail

Part one follows one file request into PowerScale: the path it travels, what PowerScale measures as it serves it, the collector that reads those measurements beside the path, and the evidence each poll leaves. It is drawn as an engineering sheet, because it is the drawing of the system.

A scan application needs file data

A user opens a scan. The application runs on a server or a VM and needs file data that is stored on PowerScale. This starts the example; no collector is involved yet.

The request travels to PowerScale

The application asks its operating system for the bytes. The VM's file client sends an SMB or NFS request. The network carries requests and file bytes between systems. PowerScale's operating system, OneFS, serves the shared file using its storage nodes.
A write follows the same route: "store these bytes at this position". One user click can cause many file operations.

The reply travels back

The file data comes back the same way: PowerScale, the network, the VM, the application. Everything the user waits for is on this route, and only part of it is inside the storage system.

Receive, process, serve, respond

PowerScale is the shared storage product; OneFS is its operating system, and several storage nodes work together. A node receives a file operation through SMB or NFS. It checks access and locates the file data or metadata. It serves the read from cache or storage, or processes the write. Then it sends data, an acknowledgement or an error back to the client.
This is a simplified flow, not an exact execution trace for every operation. Reference: Dell OneFS technical overview (see the Read lens).

Where storage latency is measured

Storage latency has a measurement boundary: it describes the work covered by that storage metric. The user also waits for the application and the rest of the path, so a delay inside this box is only one part of the user's wait.

PowerScale already keeps statistics

While serving file operations, the system maintains counters and performance measurements, and an API exposes them grouped. Activity: operation counts, rates and bytes transferred, where the endpoint supplies them. Latency: time spent processing the operations the metric covers. Who and where: client address, protocol, operation class and storage node, where reported.

A small example

Illustration only. Imagine ten measured reads whose durations add up to 120 milliseconds. Their average is 12 milliseconds per operation.

Read an average with care

That does not mean every read took 12 milliseconds, or that the user saw the scan in 12 milliseconds. A returned average alone cannot recover each request, its maximum or its percentiles. Keep the units, the operation group and the measurement interval with the number.

A separate request asks for statistics

Our collector makes a management API request on its own schedule. It is a second, separate request, outside the application's file-data path.
Two meanings of "request": the application's file request opens or changes a file; the collector's API request reads management information about activity.

Two requests, two paths

The user's file request goes to PowerScale. Separately, the collector asks the management API for statistics. The file bytes never pass through the collector, and real reads and writes carry on between collection runs.

Each poll's rows land in InfluxDB

A timer starts a poll; it is not triggered by each application request. The collector asks PowerScale for selected statistics, receives rows and metadata, and records success, partial results, a timeout or an error. The existing Python collection writes the measurements to InfluxDB.

It polls on a schedule

Reported operator settings, still to be confirmed against the deployment; they are not PowerScale defaults. Client performance every 5 seconds, to notice short changes. A full performance pass every 5 minutes: system, drives, protocols, nodes, heat, network, jobs and sessions. Configuration every 6 hours at minute 05, protection every hour at minute 35, events every hour at minute 20.
Collection time is when we asked; an event's own timestamp is when it reportedly happened. An inventory snapshot shows what was seen then, not that it stayed true for six hours.

What one row means

A row usually describes a population of operations, not one named application request. Top-N selection keeps only the selected clients. A poll time alone does not establish the metric's time window.

One click, many operations

A poll is not a trace of this request. One click can cause many file operations; our rows describe groups of operations and keep only selected clients, so we cannot assign the user's total wait to one read from those averages.

Units travel with the number

The Python collection stores these latency fields in microseconds: 1,000 microseconds is one millisecond. Every number keeps its unit, its operation group and its interval.

Zoom into the data

Now we close in on the collector and follow one poll's data from the device's response to a finding. One small synthetic example, an illustration: the addresses come from the documentation range, and the fingerprint is made up.

The raw API response

The management API answers a poll with rows of client statistics. Each row has an address, a protocol, an operation class, a storage node, an operation count and an average time in microseconds. Three rows here, illustration only.

Top-N keeps rows, each with a reason

Top-N selection keeps a few clients per poll and records why each was kept: a high rate, many bytes, a peak, or a typical row kept for comparison. The busy first row is kept for its rate, the slow third row for its peak. The second row is not selected: it stays in the response, but no saved row will carry it.

Each kept row gets an address

A kept row is addressed by a pointer into the response it came from, /client/2 (the third element, counting from zero), together with the SHA-256 fingerprint of that exact response. Pointer plus fingerprint name one row of one response, so it can be found again.

The row lifts out…

The selected row leaves the response...

…and becomes a typed point

...and is written as one InfluxDB point in line protocol: a measurement name, tags that say who and where (address, protocol, operation, node), and fields that hold the values.

Every field keeps its type and unit

Field types are explicit: a float has a decimal point, an integer ends in i, a string is quoted, a boolean is true or false. A field written once as an integer and later as a float would be refused, so the writer fixes each type. Times stay in microseconds: 48,200 microseconds is 48.2 milliseconds.

One receipt per poll

Every poll gets a run receipt: when it started and ended, its status (ok, partial or timeout), how many rows it saw, kept and dropped, and the fingerprint of the response. The fingerprint is the same one the row's address carries, so the row and the receipt point at the same response.

Sixty polls, two gaps

At one poll every five seconds, a five-minute window holds sixty polls. Two came back without data here: one timed out, one is missing. Missing means unknown, not zero: the gaps stay gaps, and the window summary says so, mean and peak over 58 of 60 polls, never a zero folded into the mean. Illustration values.

A finding opens its trail backwards

A finding, "client latency high", opens its trail backwards, one step at a time: the statistic it was judged on, the window that statistic summarises, the receipt of the poll, the selected row with its reason, and the raw response it came from.

Python path: the trail starts at the database

Two evidence paths. The existing Python collection writes rows to InfluxDB and does not keep the device response, so a finding read from the database can be traced back only as far as the saved query result.

Native path: it starts at the device

The native Node collector keeps the captured response, its fingerprint and a receipt beside the rows it writes, so the trail runs all the way back to the device response. Those Node paths are built for clients, drives and system statistics, and are not yet switched on.

Every poll leaves a receipt

Back in the big picture: every poll leaves a receipt beside its rows. Python's additive evidence and raw-response archiving are separate options, off by default; nothing in this walk-through turns them on.

Footprint keeps the trail

Footprint records how a captured response is selected, converted and used for a finding, so a finding can be followed back to its statistic, its saved rows and the captured response. On the direct-capture path that reaches the saved device response; reading existing InfluxDB data, the trail stops at the saved query result unless the collection-run join and the archived response are available and verified.
What it does not prove: a trace of our processing is not a trace of the application's file request, and not proof of physical cause. Our evidence ID identifies the collected observation, not the application's request.

Ask a question

An illustrative investigation, not a measurement from a real system. A user says the scan is slow. What do we actually know?

What is known

Illustration: the saved PowerScale response reports this client's average read latency as 12 milliseconds. That fact stands on its own evidence. Whether it is abnormal needs a baseline or a configured rule.

What is not sure, and why

Which VM produced that traffic is unresolved, because the client-to-VM mapping for that time is missing. A timed-out poll is the same kind of gap: the answer names it instead of filling it in. Only the VM claim is blocked; the latency fact remains usable. Saying why it was slow would need more evidence again: a simultaneous job or warning is a clue, not proof of cause.

The trail opens on click

Clicking the known fact opens its trail: the finding, the statistic, the saved rows and the captured response it rests on, so anyone can check the answer instead of trusting it.

One request, one measurement, one evidence trail. The file path serves the user; PowerScale measures its own work; the collector reads those statistics beside the path; and every finding can be followed back to the response it came from.

One poll, end to end: eight steps

Here is the whole native client poll once, before we open each part. Every five seconds the app schedules a slot (1). The library turns it into one operation (2). The app’s adapter fetches the client statistics from PowerScale (3). The library checks the answer and saves it raw (4). The app’s compact builder reads that saved answer and keeps only the watched values (5). The library keeps both records for a set time, then expires them (6), and every five minutes summarizes sixty slots (7). The app’s agent answers questions from those records (8). All of it is built and tested; none of it is switched on.

Two owners, one boundary

The app, above the line, is the PowerScale app: it knows the device. The library, below, is footprintjs-datapipeline: it knows how to record, and nothing about PowerScale. Each time the flow crosses the dashed line, one side calls the other through a named interface, and nothing else passes. The agent (8) is part of the app, drawn in its own colour.

Now each part in detail: the app, the library, the agent

Next we take the parts one owner at a time: the app’s steps (1, 3 and 5), then the library’s (2, 4, 6 and 7), then the agent (8). On every slide the flow stays on the left, with the step we are on lit.

The app’s part: it knows PowerScale

The app is the PowerScale app. It owns everything that knows the device: when to ask (a poll per source every five seconds), how to ask (one request, five seconds at most), what a row means (the compact builder), and the store rules (two folders, two keep times, one disk floor). It never decides how a record is saved: it hands each slot to the library.

Step 1 · Schedule: one poll per slot

A slot is one source at one scheduled instant, such as 10:00:15. The host owns the clock: it calls poll with a run ID and the slot time, once per slot, one poller per source. The sources start a little apart so they do not all ask at once. Three sources here, as an illustration.

Step 3 · Fetch: two checks before the device

Before the device is touched, the app’s adapter makes two checks. If the poll starts five seconds or more after its slot, it is refused as late, so polls never pile up behind a slow one. If free space in either store is below the floor, it is refused as storage-full, with the exact readings saved. Either way the slot gets a failed receipt, no request is sent, and nothing is retried.

Step 3 · Fetch: one request, five seconds at most

One request to the cluster’s management API for its client statistics: no redirects, at most 2 MiB, strict UTF-8, and one five-second budget for the whole poll. If the time runs out, nothing is saved and the slot shows as not collected: a gap, never a zero.

Step 5 · Compact: values and pointers, from the saved answer

Once the library confirms the raw answer is saved, it runs a second collect, and the app’s compact builder does the PowerScale part. It reads the saved answer, never the device, and writes one receipt for the slot (complete, partial, empty or failed) plus a value for each watched client. Each value points back to its row by a JSON pointer such as /client/2 and the answer’s SHA-256 fingerprint. A watched client absent from the answer is missing, not zero. Illustration values.

The app’s store settings: two folders, two times, one floor

The app also sets the rules for step 6: two separate folders (refused if they are the same, compared by real path), a keep time for each (raw never longer than compact), and a free-space floor checked before every fetch. All are required, and none has a default. The values are the operator’s decision, not ours.

The library’s part: it knows how to record

footprintjs-datapipeline is a general library: it knows nothing about PowerScale. It turns a slot into one operation, saves what the adapter returns with a receipt, keeps records for the time it is given and expires them on time, and every five minutes summarizes sixty slots, naming every gap. It is built on footprintjs, so each of its stages is recorded while it runs: the receipts and references are written as the work happens, not reconstructed afterwards.

Step 2 · Collect: one slot becomes one operation

collect() derives the operation’s ID from the slot’s own key, so the same slot always gives the same operation. Asked again with the same request, it returns the saved receipt and the device is not asked twice; the same slot with a different request is refused as a conflict. Every collect runs the same four stages: resolve, fetch (which calls the app’s adapter), check and save.

Step 4 · Save raw: checked, saved, a receipt back

The check stage validates what the adapter returned (at most 10,000 records and 8 MiB) and gives each record a stable reference. The save stage writes it to the raw store and returns a receipt: committed, partial, failed or unknown. Unknown is followed by a lookup, never a guess. The store is a folder: a small SQLite ledger (which operation, its references and its expiry, never the content) and one compressed file per operation.

Step 6 · Keep & expire: on time, and the receipt stays

Raw answers are kept a short time and compact records longer, with the times the app set. A cleanup worker, separate from the polls, removes expired data: at most 100 operations and ten seconds per sweep. It writes a tombstone first, so reading an expired record answers “expired”, with when it was accepted and that its data was deleted, never “not found”.

Step 7 · Summarize: sixty slots, one summary, gaps named

Every five minutes, derive() reads sixty saved compact slots and writes one summary: count, mean, variance, minimum, maximum, first and last. It also records coverage: expected, received, missing, failed, partial and empty. Here two slots were not collected, so coverage is 58 of 60 and the gaps stay gaps; a real zero is a valid value. Illustration values.

Every number traces back to its row

Each summary keeps its own saved trace: the decisions, requirements and statistics behind it. From a statistic you can open the values and receipts it used, then the compact record, then the saved answer and the exact row, by its pointer and fingerprint. Every link is a reference written while the stage ran, because footprintjs records the run as it goes; nothing is rebuilt afterwards. So a number can be checked instead of trusted.

The agent’s part: it answers from the record

The agent is part of the app, built with agentfootprint. A question picks a skill; the skill names the tools and their order; each tool result says what it checked and what it could not; and the answer carries a standing (known, not sure, or ask) worked out by code from the run’s record. Today its PowerScale tools read the live path, InfluxDB; reading these native summaries is the next step.

At run time: a skill, its tools, an answer

At run time a question arrives. agentfootprint routes it to a skill: for slowness, triage. The skill says which tools to call and in what order: what the cluster itself reports, which operation class, which clients. The answer comes back with a standing. The whole run is kept as a record (the skill it read, each tool call and result, and what was absent), and it opens later in the Lens tab.

Three PowerScale skills and their tools

The app’s agent has three PowerScale skills. Triage asks whether anything is wrong, whether it is slow, and who is talking; inventory covers what is there; protection covers copies and snapshots. Each skill lists its tools; these are the main ones. All of them read the live path today.

Today: InfluxDB. Next: these summaries

Today the PowerScale tools read what the Python collector saved: InfluxDB and prepared history. The native summaries are built, but no tool reads them yet. The next step is a tool that reads the five-minute summaries and their receipts from the compact store. That brings coverage with every number (“58 of 60 slots”, not just a mean), a reason for every gap, and a path from any number back to its row. This wiring is still to do.

The answer says what is known, what is not, and why

An illustration of an answer once that wiring exists. Known: read latency averaged 46 ms over 58 of 60 slots. Not sure: two slots were not collected. Why: the two gaps, each with its receipt. The model does not write the standing: agentfootprint works it out from what the tools checked and what they found absent.

What agentfootprint adds

Skills and tools are declared, so the record shows which skill ran and which tools it called. An absence stays an absence: a missing value is carried as missing, never read as zero. The standing (known, not sure, ask) is worked out by code from what was checked. And every run is recorded, so it can be opened later in the Lens tab, call by call.

Part three is what we keep: the four things stored, how many bytes they take, and the steps that keep them small. Drawn as a ledger, because it is bookkeeping. The stamp is the rule: when data expires, its receipt stays.

Four things are kept

Two folders, two stores. The raw store keeps each answer from the device, compressed, for a short time. The compact store keeps each slot’s receipt with the watched values and their pointers back, for longer, plus the five-minute summaries with their own traces. Both keep a small ledger, the bookkeeping: which operation, when it was accepted, when it expires. The bookkeeping stays after the data expires, so an expired record can still say “expired” rather than “never existed”.

One poll on disk: about 13 KB

Measured on a local probe of 2,000 polls with 256 rows and one watched client: the compressed answer is about 8.6 KB, the compact receipt about 2.2 KB, and the bookkeeping about 2.2 KB. The first two expire; today the bookkeeping does not.

A fleet day: about 3.1 GB

Arithmetic, not a measured fleet day: 14 sources polled every five seconds make 241,920 polls a day. At the measured sizes that is about 2.07 GB of answers, 0.53 GB of receipts and 0.54 GB of bookkeeping a day. More watched clients make the receipts larger. The full-day storage run, on its own disk, will measure it.

Kept a week or a month: about 30 GB, then flat

With example keep times (the operator chooses the real ones), answers kept seven days take about 14.5 GB and receipts kept thirty days about 15.9 GB. Once the stores are full, old data leaves as new data arrives, so that part stays flat at about 30 GB. The bookkeeping is different: today it never expires, so it grows by about 0.54 GB a day, roughly 16 GB a month. That is the part we are working on next.

Per poll: record less, compress, keep values

Three choices keep each poll small. First, this path records no per-row trace: the old full-trace path, at only 50 rows, came to about 30 GB a day (8.0 GB of packed data plus 21.8 GB of traces, a straight-line projection from a ten-minute run). Second, each answer is one gzip file. Third, the compact store keeps only the watched values and pointers (about 2.2 KB), not the rows.

Over time: raw goes first, expiry, summaries

Raw answers are never kept longer than the compact records that point at them. A cleanup worker expires data on time, in small sweeps, and leaves a receipt. And every five minutes sixty slots become one summary, so long questions read summaries, not every slot. The keep-time rules and the cleanup wiring are in review; the rest is built.

The bookkeeping: seal it, then choose how long

The bookkeeping is the one part that still grows. A draft seals it into compact, checksummed files, 4.43 times smaller including overhead: about 0.5 KB a poll instead of 2.2, or about 122 MB a day instead of 0.54 GB, by arithmetic. It does not yet compact a running store. The last step is choosing how long history is kept; until then even sealed bookkeeping grows, about 44.5 GB a year. That length is the operator’s decision, and it waits on a rule for retiring whole periods.

Part four is what it costs and how it grows: the time per poll, memory, summaries and cleanup; then the load at fleet scale, what grows with time, and what still has to be proven. Drawn as an instrument, because these are readings. On the screen, each thin spike is one poll, drawn to scale: 45 ms out of every five seconds.

One poll: 45 ms of a 5-second slot

Measured on a laptop with a synthetic device, a single poll at 256 rows takes a median of 45 ms (35 ms at 50 rows), including saving both records: under one percent of its five-second slot. For contrast, the old full-trace path, with 14 sources polling at once at only 50 rows, had a 95th percentile of 3.49 seconds and 24 deadline misses in ten minutes, and at 256 rows its memory guard stopped it. The two runs are not like-for-like; the fleet-rate test of the new path is still to run.

Memory: about 290 MB for fourteen pollers

One process running fourteen pollers over one pair of stores, plus the cleanup worker, peaked at about 290 MB over 1,400 polls; with cleanup off, about 276 MB. In a separate 3,000-poll probe the main heap stayed flat, 38.4 to 38.6 MB from poll 600 to 3,000. The old path peaked at 1.96 GB at 50 rows and reached 2.45 GB at 256 rows before it was stopped. These are short runs; flat memory over a whole day is still to prove.

One summary: 261 ms

Summarizing one five-minute window (sixty slots, sixteen watched series) took 261 ms in the test fixture, and its saved trace is about 0.8 MB, well under the 8 MiB cap. The plan runs summaries in their own worker, never on the poll path; that worker is still to build.

Cleanup runs beside the polls

Cleanup has its own worker: at most 100 operations and ten seconds per sweep, and it is never queued ahead of a poll. Still being checked: in the rerun on its own disk, one save hit the five-second limit. Diagnostics were added and no safeguard was loosened; that run’s record will show the cause.

The load: 241,920 polls a day

Fourteen sources, one poll every five seconds each: 17,280 slots a day per source, 241,920 polls a day, about 2.8 a second. Meanwhile the live path, the Python collector, keeps running unchanged; this one stays switched off.

Staggered, not all at once

The plan staggers sources across the slot: source number times five seconds divided by fourteen, so one source starts every 357 ms. The old test dispatched all fourteen in the same instant, so every poll and summary competed together; that is where it missed deadlines and ran out of memory. The staggering dispatcher is still to build.

Every poll has the same ceiling

Each poll is bounded: five seconds, a 2 MiB answer, 10,000 records, an 8 MiB record and at most sixteen watched series. History lives in the stores on disk, not in memory, so a poll on day 300 should cost what a poll on day 1 costs. The day-long run will check that.

One more source: one more poller

Adding a source adds one poller and 17,280 polls a day. By arithmetic from the measured sizes, that is about 186 MB a day of answers and receipts, which expire, and about 38 MB a day of bookkeeping today (about 9 MB once sealed), which stays.

What grows: the bookkeeping, until history has a length

An illustration by arithmetic. In today’s format the bookkeeping for fourteen sources grows about 195 GB a year; sealed, about 44.5 GB a year. With a kept-history length, for example thirteen months (a year-over-year comparison plus a month), it stops growing after that. The length is not chosen yet.

Still to prove

Before anything is switched on: a full day of storage on its own disk (running now; the last attempt ran out of room on a shared laptop disk), then one hour at 50 rows and one at 256 rows, then 24 hours at 256 rows. To pass: at least 99.9% of slots saved or explicitly failed, the 99th percentile under five seconds, flat memory, and every summary done within a minute of its window. The result will be “passes on this machine at this rate”, not a fleet guarantee.

Three owners, three jobs

The app knows PowerScale: when to ask, how to ask, what a row means, and the store rules. The library knows how to record: one operation per slot, a receipt for everything, expiry on time, and summaries every five minutes. The agent answers from the record, with a standing on every answer.

Why footprintjs

Why build it on footprintjs. Every step leaves a receipt, recorded while it runs, not rebuilt afterwards. A gap is named, never a zero: not collected, missing, invalid or empty, each with its reason. Every number traces back: summary, receipt, saved answer, the exact row. And every answer says how sure it is, and why.
