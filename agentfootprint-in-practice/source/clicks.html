The start: an AI model that reads and writes text

This is how an agent grows, one problem at a time, shown on a real one: a storage-operations chat app built on the agentfootprint library, which we call "the app". First, three words. The model is a large language model: it reads text and writes text. Everything it reads before it answers is the prompt, and every word in it costs time and money. And it has never seen your data. The whole app stays on this board the entire time: the model in the middle, and dashed boxes for what comes later. Each part also has its own look; only the paper changes, never the board.

Tools: how the model reaches real data

To reach real data, the app gives the model tools. A tool is a small program with a name and a description; the model asks for it by name, the app runs it and puts the result into the prompt. This app starts with two: an inventory tool and a latency tool.

It works: one question, one tool, one answer

With two tools, the model picks the right one: it calls the latency tool, the tool reads the data, and the answer comes back. The answer here is an illustration. This is where most demos stop. The dashed boxes are what the app needed next, as it grew.

Level 1: ninety-two tools, and the wrong one picked

The app grew to 92 tools over its data: fabric ports and zones, arrays, NAS clusters, backups, VMs, the network sensor, collection health. Offered all at once, every tool description rides in every prompt. Prompts get long, and the model has to pick one tool out of 92. Here it picks the event log instead of latency, and answers a different question: nothing happened, so it looks fine. The wrong pick is an illustration.

Fix: pick a skill first, then its few tools

Skills. The model first sees a menu: 25 skills, each a name and a one-line description, offered through one tool, read_skill. Reading a skill brings its steps into the prompt and makes its tools available on the next call: about 4 tools (between 1 and 17), never all 92. With the skill read, the model has the latency tool in front of it again, and the answer changes back to the right one. In the app the model chooses the skill; rules and a scorer can choose first, and a near-tie falls through to the model. On top, agentfootprint can narrow the tools further with a classifier: 57% fewer tool bytes over 8 questions with the same verdicts, on Sonnet 5 in one pass ("it pays on bytes, not on judgment"). The app keeps that option off by default.

Level 2: it doesn’t know where facts live

A question needs a link that one tool result does not hold. The VM inventory knows the VM, its host and its datastore, but not the array behind them. With nothing that says where that fact would be found, the model guesses instead of looking. Notice where the problem sits on the board: in the slot its fix will fill.

Fix: a map of what exists, and where

The map. agentfootprint's defineOntology turns the app's map of its world into data: 46 terms, 47 relations and 20 sources, each saying which tool, in which skill, finds it. It rides at the end of every prompt. It is a map, not a tool: it never fetches anything. The guess is struck through, and the answer is looked up instead. It costs about 6.5 thousand tokens a call. We measured it honestly: on 8 "no data" questions with Sonnet 5, tool calls fell from 13 to 6, but almost all of that came from one question, so the benefit is mixed. What it reliably gives is a place to say where a missing fact would be found.

Level 3: big tables, and math by eye goes wrong

Some answers are tables: every VM disk, every port, thousands of rows. They pour into the prompt, and the model is asked for totals and percentages. The app's own words: a model adding up a wide table by eye gets it wrong. The numbers come out plausible and wrong. The numbers here are an illustration.

Fix: let code do the math

A code tool. The model writes a short script; agentfootprint's code runner runs it in a separate process. In the app it runs with no inherited secrets, for at most 30 seconds, and returns up to 8,000 characters. The model never adds the numbers itself, and the answer changes from a guess by eye to a computed number. The app is careful to call this process isolation, not a sandbox. And where the numbers matter most, the app goes one step further: the model only picks one of three named calculations, and the app computes it from the table and checks the result; the model supplies no rows, formula or code. The picker passed 29 of 29 wordings on Haiku 4.5. A free-form script once invented two datastores and a percentage it never computed, which is why the checked calculation comes first and free code is the fallback. The table, though, is still in the prompt: that is the next level.

Level 4: the whole table is sent, again and again

The script fixed the math, but the table still passes through the prompt: thousands of rows fill the context, and every following question carries them again, so every call costs more and the model skims. The table here is an illustration.

Fix: keep the table, send a short label

References. The table goes into agentfootprint's artifact store, and the model gets a ticket: the reference, the row count, the column names and where the data came from, capped in size and without a single cell value. The rows never reach the prompt. The code tool asks for the table by reference: the library stages it as a file before the script runs. The follow-up is answered without carrying the rows again. In the app, every table is withheld this way, at any size.

Level 5: “Why node 3?”, and the details are gone

Users ask follow-ups about an earlier answer: why that node, what about the second one. The evidence was in the earlier run, which the prompt no longer holds, so the model answers from memory and guesses.

Fix: record every run, and let the model look back

The run log. agentfootprint records every run: which tools ran, what each returned and why each was called. A self-explain skill gives the model, for that one step, 15 trace tools bound to the previous run, so a follow-up is answered from the record, and the guess gives way to what run 1 actually saw. In the app the conversation lives on the server, with a small carry of earlier receipts, never raw rows.

Level 6: a guess reads exactly like a fact

The last problem is trust. In a long answer, a guess from step six reads exactly like a fact from step two. Here the first sentence was checked and the second was assumed, and nothing in the wording tells them apart. Illustration.

Fix: note why each call was made, then mark the answer

The findings ledger. With agentfootprint's findings, every tool call carries a short reason: is it direct or exploratory, and what does it expect. Earlier results are marked fact, open, noise or ruled out. No extra model calls, and nothing is inferred. The flat answer is struck through; the new one says what is known, what is not sure and what to ask, worked out from those rows, never from the model's confidence. Measured honestly: on real models over ten runs, how often noise was cited barely moved, so the ledger's value is that you can see which is which, not that the model got better at it. The rows here are an illustration.

The whole app: six problems, six fixes

Six levels, six fixes, and the board is full: skills, the map, code, references, the run log and the ledger, around the same model. None of these problems is special to this app; they are what an agent meets as it grows. Next: whose is each fix?

Draw the line: the library provides the how

Draw the boundary. Everything in green is agentfootprint: the agent loop and tool calls, defineSkill with its read_skill menu and routing, defineOntology for the map, the artifact store and references, the code runner and the helpers for checked operations, recordings and the self-explain trace tools, and the findings ledger with the answer's standing. None of it knows anything about storage.

The app brings the what: its skills and their tools

And everything in purple is the app: its 25 skills and their steps, its 92 tools over its own data, the map's data, its three checked operations, and its screen. It also decides which results are tables and keeps its sessions in its own database. The library is the how; the app is the what.

That is what agentfootprint is for

That is what the library is for. An agent meets these problems as it grows; agentfootprint solves them once, so an app brings only what it knows: its skills, their tools, its map and its data. Every run can also be seen in the Lens, a companion package, agentfootprint-lens. agentfootprint is open source, version 10.10.0 on npm, MIT licensed.

What it does not claim

And what it does not claim. It does not make the model right. It records what was checked, what was guessed and what is missing, and the answer says so. Measured on real models, the picture is mixed: the checked-calculation picker passed 29 of 29 wordings on Haiku 4.5; the map cut tool calls from 13 to 6 over 8 questions on Sonnet 5, but almost all of that came from one question; and over ten runs the ledger did not make the model cite noise less often. Some fixes pay off directly; others are about seeing which is which.

Today: the math runs while the user waits

What comes next connects this deck to the PowerScale deck. Today, a question about an average or a total makes the model write a short program, the app run it over the raw samples, and check the result, all while the user waits: four steps at question time. The steps are counted here, not timed.

Next: a stats builder sums the data as it arrives

The pipeline in the PowerScale deck already collects every five seconds. Its stats builder sums the samples as they arrive: every five minutes, sixty samples become one summary (count, mean, variance, minimum, maximum) with its coverage, and a sample that was not collected stays a named gap, never a zero. Each summary keeps its trail back to the samples and the raw rows, because footprintjs records the run as it goes. As of 21 October 2026 it is built and tested, and switched off. Then an answer is one lookup away

So at question time the model has one step left: read the summary, through a new summaries tool. The answer carries what is known (the average over 58 of 60 samples) and what is not (two samples missing, each with its reason).
