agentfootprint assembles the request, in a fixed order
one adapter per provider
its code and its data
Where does a tool’s description go?In the tools part of every request, beside its name and inputs. The code stays with the app.
How does the model use a tool?It writes a tool call: the name and the inputs. The app runs it and adds the result as text.
What does reading a skill return?Only “activated”. On the next call the skill’s instructions join the system prompt.
Why do some lines go last?The unchanged start is reused, so what changes goes after it; and a line where the model decides is followed.
one requestAn AI model reads text and writes text. Each time, the app sends it one request in three parts and gets one reply back.
the system promptThe system prompt is the app’s standing instructions. It comes first and barely changes from call to call.
the messagesThe messages hold the conversation. Asked whether the NAS cluster (a group of storage servers) is slow, a model with no tools can’t look.
a toolThe tools part lists what the app can run for the model: a name, a description and the inputs it takes. The code stays with the app.
the callThe model can’t run anything. It replies with a tool call: a tool’s name and its inputs, as JSON.
the resultThe app runs the code and adds the result to the messages, as text. Then it sends the whole request again: call 2.
many tools92 tools means 92 descriptions in every request: more to read on every call, slower and costlier, and one pick out of 92.
skillsA skill is one job’s instructions plus its tools, like NAS triage. One tool, read_skill, lists the skills in its own description.
reading a skillCalling read_skill returns only “activated”. On the next call, the skill’s instructions join the system prompt.
scopingBy default a skill’s tools stay listed from the first call. Switch on scoping, and the request lists only the active skill’s tools.
the mapThe map of the app’s world goes last in the system prompt, under a header that says it is data, so the model looks things up in it rather than taking orders.
big resultsA result over the size limit stays with the app. The model gets a short stand-in with a reference it can pass to another tool.
notes at the endSome notes go at the very end, on each call: the time, a reminder, a check of the draft. Placed where the model decides, they are followed.
the ledgerWith the ledger on, every tool gets an optional _findings input: why this call. What the model declared comes back as one DATA line, last.
cachingThe provider can reuse a request’s unchanged start: faster and cheaper. So anything that changes, like the time, goes at the end.
four providersEach provider (Anthropic, OpenAI, Amazon, Google) wants the same request in its own shape. One adapter each translates it.

Where does a tool’s description go?In the tools part of every request, beside its name and inputs. The code stays with the app.
How does the model use a tool?It writes a tool call: the name and the inputs. The app runs it and adds the result as text.

one requestAn AI model reads text and writes text. Each time, the app sends it one request in three parts and gets one reply back.
the system promptThe system prompt is the app’s standing instructions. It comes first and barely changes from call to call.
the messagesThe messages hold the conversation. Asked whether the NAS cluster (a group of storage servers) is slow, a model with no tools can’t look.
a toolThe tools part lists what the app can run for the model: a name, a description and the inputs it takes. The code stays with the app.
the callThe model can’t run anything. It replies with a tool call: a tool’s name and its inputs, as JSON.
the resultThe app runs the code and adds the result to the messages, as text. Then it sends the whole request again: call 2.
many tools92 tools means 92 descriptions in every request: more to read on every call, slower and costlier, and one pick out of 92.
skillsA skill is one job’s instructions plus its tools, like NAS triage. One tool, read_skill, lists the skills in its own description.
reading a skillCalling read_skill returns only “activated”. On the next call, the skill’s instructions join the system prompt.
scopingBy default a skill’s tools stay listed from the first call. Switch on scoping, and the request lists only the active skill’s tools.
the mapThe map of the app’s world goes last in the system prompt, under a header that says it is data, so the model looks things up in it rather than taking orders.
big resultsA result over the size limit stays with the app. The model gets a short stand-in with a reference it can pass to another tool.
notes at the endSome notes go at the very end, on each call: the time, a reminder, a check of the draft. Placed where the model decides, they are followed.
the ledgerWith the ledger on, every tool gets an optional _findings input: why this call. What the model declared comes back as one DATA line, last.
cachingThe provider can reuse a request’s unchanged start: faster and cheaper. So anything that changes, like the time, goes at the end.
four providersEach provider (Anthropic, OpenAI, Amazon, Google) wants the same request in its own shape. One adapter each translates it.
