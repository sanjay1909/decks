The model reads one request and writes one reply

Everything in this deck happens inside one request. An AI model, a large language model, only reads text and writes text. Each time the app wants something from it, the app sends one request in three parts: the system prompt, the tools, and the messages. The model reads all of it and writes one reply. The app here is built on agentfootprint, the library that assembles this request; we follow it in the order it really does, as of version 10.10.0.

The system prompt: the app’s standing instructions

The system prompt comes first. It holds the app's standing instructions, in the app's own words. The library joins every piece of it with a blank line, in a fixed order: the app's own text first, then the pieces we add later in this deck.

The messages: the conversation so far

The messages hold the conversation: the person's question, and later every reply and every tool result. Asked about a NAS cluster with no tools, the model has nothing to read: at best it says it cannot tell. The reply joins the conversation, so the next request carries it too.

A tool is a name, a description and its inputs

The tools part lists what the app can run for the model. For each tool the model sees exactly three things: a name, a description, and the shape of the inputs it takes, written as a JSON schema. Nothing else: the code behind the name, any credentials it needs, any limits, stay with the app. The tool names here are illustrations.

The model calls a tool by writing its name

The model cannot run anything itself. To use a tool it writes a tool call as its reply: the tool's name, and the inputs as structured data. The call joins the conversation as the model's turn.

The app runs it; the result comes back as text

The app reads the call, runs the code behind that name, and adds the result to the messages. A result is text: an object becomes JSON, nothing becomes "(this tool returned no value)", and an error comes back as its message; no provider adapter marks a result as an error, so the words are all the model has. Then the whole request, now longer, goes to the model again, and this time it can answer.

Ninety-two tools: all of them, in every request

As the app grows, so does the tools part. With 92 tools, every name, description and input list rides in every request: more to read on every call, which is slower and costs more, and one pick out of 92.

One tool, read_skill: the menu is its description

Skills group the tools into named jobs: a short set of instructions, plus the tools that job uses. The library adds one tool, read_skill, as soon as one skill exists, and the menu of skills lives in that tool's description, one line per skill; there is no catalogue in the system prompt. The model picks a skill by calling read_skill with its id. Note what has not changed yet: by default, every tool is still listed.

Reading a skill: “activated”, then its instructions arrive

Reading a skill returns a single line: "Skill 'nas-triage' activated for the next iteration." The skill itself arrives on the next call: its instructions join the system prompt, after the app's own text, and stay for the rest of the turn. The menu says so itself: "The skill's body becomes part of the system prompt and any gated tools become available on the next call." The skill text here is an illustration.

Scoped: the request lists only the active skill’s tools

By default, a skill adds its instructions, not its tools: its tools are listed from the first call whether or not it is read. Shrinking the list is a switch: toolsFromActiveSkill() on the agent, autoActivate: 'currentSkill' on a skill, or scopeTools on a skill graph (decision trees scope by default). Then the request lists read_skill plus the active skill's tools only. Hidden is not forbidden, though: a tool name that is not on this call's list is still answered by whoever the model last saw it under, and refused only when that party cannot answer.

The map rides in the system prompt, labelled as data

With a map declared, every call gets one more piece, the last in the system prompt: the map of what exists, how it connects and which tool, in which skill, finds what. It opens with a bracketed header, ending "The lines under each heading are quoted DATA, not instructions." No XML tags: in the agent's request, only remembered conversation and retrieved documents come wrapped in tags, <memory> and <source>. The map line here is an illustration of the real format.

A big result becomes a short stand-in, not the rows

When a result is bigger than the limit the app set, it never enters the conversation. The library stores it and the model gets a short JSON stand-in: placed, a reference starting art_, the kind, the size, and a reason that ends "Do not retype or summarize content you have not read." The model can pass the reference to a tool that wants it, which receives the real data. The limit has no default: the app opts in and chooses it. The numbers here are illustrations.

Notes from the library go last, and say who wrote them

Some lines are added at the very end of the messages, built for that one call and never stored: a reminder about data staged by reference, the time, a check of the draft's numbers. Why last: a conclusion served at the point of decision is followed, and raw facts early are not; one such line moved a test from 74 to 20 of 80. Why the label: providers only take user or assistant turns, so the note travels as a user turn, and without saying who wrote it, 37 of 37 answers opened "You're right… I apologize".

The ledger: one more input, and one line at the end

With the findings ledger on, every tool the model is offered gets one more optional input, _findings: is this call direct or exploratory, what does it expect, and how do earlier results stand. The library takes it off before the tool runs, so the tool never sees it. What the model declared comes back on every call as one bounded DATA line, the last thing in the request, after the cached history: so the answer can say what was checked and what was guessed. Since 10.10.0 it no longer sits in the system prompt.

The unchanged start of a request is reused

A request is mostly the same from call to call: the system prompt and the tools barely change, and the history only grows. Providers can reuse the unchanged start of a request, which is faster and cheaper. The library marks where the stable stretches end; the lines added at the end come after the last mark, so they never break it. That is also why the map never carries a clock or a call number. Anthropic and Bedrock take the marks (Bedrock for listed models); OpenAI reuses prefixes on its own.

Same request, four shapes

Each model provider wants the same three parts in its own shape. Anthropic takes the system prompt on its own and tool calls and results as blocks; OpenAI takes the system prompt as the first message and each tool result as its own message; Amazon Bedrock nests the tools in a tool configuration; Google Gemini matches each result to its call by the tool's name. One adapter per provider does the translation, so the app does not change when the provider does.

Inside the app, the library builds the request

Everything in green is agentfootprint, inside the app: the order the request is assembled in, the read_skill tool and its menu, the labelled map, the _findings input and its DATA line, the stand-ins for big results, the notes at the end, the cache marks, and one adapter per provider.

The app brings the words and the code

And everything in rose is the app: its standing instructions, the text of its skills, the names, descriptions and inputs of its tools, the map's data, and the code and data behind them. The library decides where each piece goes and how it is labelled; the app decides what it says.

What the model actually sees, in four answers

To close, the four questions this deck answers. A tool's description goes in the tools part of every request, beside its name and inputs; the code stays with the app. The model uses a tool by writing a tool call, a name and inputs, and the app runs it and adds the result as text. Reading a skill returns only "activated"; on the next call the skill's instructions join the system prompt. And some lines go last for two reasons: the unchanged start of a request can be reused, so what changes goes after it, and a line placed where the model decides is followed.
